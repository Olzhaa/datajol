M2.3 Git & GitHub: Git және GitHub негіздері

Git — кодтың өзгерістер тарихын сақтайтын жүйе, ал GitHub — сол тарихты бұлтта сақтап, бөлісетін орын. Аналитик үшін бұл SQL скрипттері мен ноутбуктерді сақтау, командамен жұмыс және портфолио. Тапсырмаларда терминалға қандай команда жазатыныңызды тексереміз.

Тіркелмей бірінші сабақты бастау Барлық тапсырмалар

1. Неге Git керек?

Таныс жағдай: report_final.xlsx, report_final_v2.xlsx, report_final_ACTUAL.xlsx. Қайсысы соңғы? Не өзгерді? Git осы мәселені шешеді.

  • Repository (репозиторий) — жобаның папкасы және оның толық тарихы.
  • Commit — жобаның белгілі бір сәттегі «суреті» және не өзгергені туралы хабарлама.
  • Branch (тармақ) — негізгі нұсқаны бұзбай, бөлек жұмыс істейтін желі.
  • Remote — репозиторийдің бұлттағы көшірмесі (GitHub, GitLab).

Үш аймақ

Working directory  ──git add──▶  Staging area  ──git commit──▶  Repository
(өзгертілген файлдар)            (келесі commit-ке дайын)        (сақталған тарих)
Git — бағдарлама (компьютерде), GitHub — сайт (бұлтта). Git-ті GitHub-сыз да қолдануға болады.

Аналитикке Git не береді?

  • Тарих: үш ай бұрын есепте қандай сүзгі болғанын бір командамен көресіз.
  • Қауіпсіз эксперимент: жаңа тәсілді бөлек тармақта байқап, нәтиже шықпаса, жай ғана тастай саласыз.
  • Командалық жұмыс: бірнеше адам бір SQL файлын бір-бірінің жұмысын өшірмей өзгерте алады.
  • Портфолио: GitHub профиліңіз жұмыс берушіге сіздің нақты жобаларыңызды көрсетеді.

Git нені жақсы сақтайды?

Git мәтін файлдарымен ең жақсы жұмыс істейді: .sql, .py, .md, .csv (шағын). Ол әр жолдың қалай өзгергенін көрсетеді. Excel немесе Power BI файлдары (.xlsx, .pbix) екілік форматта, сондықтан Git олардың «өзгергенін» ғана біледі, нені өзгергенін көрсете алмайды. Сол үшін есептің логикасын (SQL, Python) мәтін файлдарында ұстаған тиімді.

Бұл модульдегі командаларды сайттағы оқу терминалында жазасыз. Өз компьютеріңізге Git орнатып, сол командаларды қайталап көрсеңіз, тез есте қалады.

Сабақты интерактивті түрде ашу →

2. init, status, add, commit

git init                         # папкада жаңа репозиторий бастау
git status                       # не өзгерді, не staging-те тұр
git add sales.sql                # бір файлды staging-ке қосу
git add .                        # барлық өзгерістерді қосу
git commit -m "Айлық табыс сұрауын қостым"

Бірінші рет баптау (бір рет қана):

git config --global user.name "Асқар Нұрлан"
git config --global user.email "askar@mail.kz"

Жақсы commit хабарламасы

  • Не және неге өзгергенін қысқа айтады: «Тазалауда refund-тарды алып тастадым».
  • Нашар: «fix», «update», «asdf».
  • Бір commit — бір логикалық өзгеріс.

Бір жұмыс циклі

Күнделікті жұмыс осы қадамдардан тұрады:

  1. Файлды өзгертесіз (мысалы, sales.sql-ге жаңа сүзгі қосасыз).
  2. git status: Git файлды «modified» деп көрсетеді.
  3. git add sales.sql: өзгерісті келесі суретке дайындайсыз.
  4. git commit -m "...": суретті тарихқа сақтайсыз.

Staging аймағы неге керек?

Бір уақытта екі түрлі нәрсені өзгерттіңіз дейік: тазалау сұрауындағы қатені түзеттіңіз және жаңа графикке дерек дайындадыңыз. Staging арқылы оларды екі бөлек commit етесіз: алдымен git add cleaning.sql және commit, сосын git add chart.sql және commit. Тарих таза болады, ал керек болса, тек біреуін кері қайтара аласыз.

git add . ыңғайлы, бірақ ол барлық файлды, оның ішінде кездейсоқ файлдарды да қосады. Commit алдында git status арқылы тізімді тексеріңіз.

Сабақты интерактивті түрде ашу →

3. Тарих: log, diff, restore

git log --oneline          # commit-тер тізімі, қысқаша
git diff                   # әлі staging-ке қосылмаған өзгерістер
git diff --staged          # staging-тегі өзгерістер
git restore report.sql     # файлдағы сақталмаған өзгерістерді болдырмау
git restore --staged a.sql # файлды staging-тен шығару (өзгеріс қалады)
git revert a1b2c3d         # бұрынғы commit-ті жаңа commit арқылы кері қайтару
git restore сақталмаған өзгерістерді біржола жояды. Абай болыңыз. Ортақ тарихты өзгертпеу үшін жарияланған commit-ті revert арқылы қайтарыңыз.

Commit-ке қарап шығу

git log --oneline әр commit-ті қысқа хэшпен көрсетеді:

a1b2c3d Тазалауда refund-тарды алып тастадым
9f8e7d6 Айлық табыс сұрауын қостым
4c5b6a7 Жобаны бастадым

Белгілі бір commit-те не өзгергенін көру үшін git show a1b2c3d, ал файлдың тарихын көру үшін git log -- sales.sql жазамыз.

diff-ті оқу

git diff нәтижесінде - белгісімен басталатын жолдар жойылған, + белгісімен басталатындар қосылған:

-WHERE status = 'paid'
+WHERE status = 'paid' AND amount IS NOT NULL

Commit жасамас бұрын diff-ті әрқашан қараңыз: кездейсоқ өзгеріс немесе ұмытылған тест жолы бар-жоғын көресіз.

Қай команданы қашан?

  • Файлды бұздыңыз, commit жоқ → git restore файл.
  • Қате файлды staging-ке қостыңыз → git restore --staged файл.
  • Қате commit GitHub-та тұр → git revert хэш.

4. Тармақтар: branch, switch, merge

Жаңа талдауды бөлек тармақта жасаймыз, негізгі main тармағы таза қалады.

git branch                      # тармақтар тізімі
git switch -c churn-analysis    # жаңа тармақ құрып, соған өту
# ... жұмыс, add, commit ...
git switch main                 # main-ге оралу
git merge churn-analysis        # тармақты main-ге біріктіру
git branch -d churn-analysis    # біріктірілген тармақты жою

Merge conflict

Екі тармақта бір жол әртүрлі өзгерсе, Git өзі шеше алмайды. Файлда белгілер пайда болады:

<<<<<<< HEAD
WHERE status = 'paid'
=======
WHERE status IN ('paid', 'refund')
>>>>>>> churn-analysis

Дұрыс нұсқаны қолмен қалдырып, белгілерді өшіресіз, сосын git add және git commit.

Ескі нұсқаларда git checkout -b name жазылады, ол git switch -c name-мен бірдей.

Тармақтың тәжірибедегі мысалы

Сіз main-де жұмыс істейтін айлық есепті жүргізесіз. Басшы жаңа churn талдауын сұрады. Егер оны main-де бастасаңыз, жартылай дайын код есепті бұзуы мүмкін. Сондықтан churn-analysis тармағын ашасыз. Осы уақытта айлық есепке шұғыл түзету керек болса, git switch main арқылы оралып, түзетіп, қайтадан тармағыңызға ораласыз.

Тармақ атауы

Атауды қысқа, сызықшамен және мағыналы етіп беріңіз: churn-analysis, fix-refund-filter. Бос орын мен кириллицаны қолданбаған дұрыс: кейбір құралдар оларды дұрыс өңдемейді.

Конфликттің алдын алу

  • Тармақтарды ұзақ ұстамаңыз: бірнеше күнде біріктіріп отырыңыз.
  • Жұмысты бастамас бұрын main-нің соңғы нұсқасын алыңыз.
  • Бір файлды екі адам бір уақытта өзгертпеуге келісіңіз.

5. GitHub: clone, push, pull, pull request

git clone https://github.com/user/repo.git   # бұлттағы репозиторийді көшіру
git remote add origin https://github.com/user/repo.git
git push -u origin main                      # жергілікті commit-терді жіберу
git pull                                     # басқалардың өзгерістерін алу

Pull request (PR)

  1. Жаңа тармақта жұмыс жасап, git push -u origin my-branch.
  2. GitHub-та Pull request ашасыз: «осы өзгерістерді main-ге қосуды сұраймын».
  3. Әріптес code review жасайды, ескертпе қалдырады.
  4. Мақұлданған соң Merge.

Fork — басқа адамның репозиторийін өз аккаунтыңызға көшіру (ашық жобаларға үлес қосу үшін).

Жергілікті және бұлттағы репозиторий

Commit алдымен тек сіздің компьютеріңізде сақталады. git push оны GitHub-қа жібереді, ал git pull басқалардың commit-терін сізге әкеледі. Push жасамасаңыз, әріптестер сіздің жұмысыңызды көрмейді, ал компьютер бұзылса, жұмыс жоғалады.

Code review-де не қаралады?

  • SQL логикасы дұрыс па: сүзгілер, JOIN түрі, топтау?
  • Сандар бұрынғы есептермен сәйкес келе ме?
  • Код түсінікті ме: атаулар, түсініктемелер?
  • Құпия дерек (пароль, жеке ақпарат) кездейсоқ қосылмады ма?

Review — сынау емес, бірге сапаны көтеру тәсілі. Ескертпеге «неге?» деп сұрау да, өз шешіміңізді түсіндіру де қалыпты.

git push қате берсе («rejected»), көбіне GitHub-та сізде жоқ жаңа commit-тер бар деген сөз. Алдымен git pull жасап, сосын қайта push етіңіз.

6. .gitignore, README және портфолио

.gitignore

Git-ке не сақтамау керектігін айтатын файл:

# .gitignore
.env                 # құпия кілттер мен парольдер
data/raw/*.csv       # үлкен немесе жеке деректер
__pycache__/
.ipynb_checkpoints/
Парольді немесе API кілтін бір рет commit жасасаңыз, ол тарихта қалады, тіпті кейін жойсаңыз да. Кілтті бірден ауыстырыңыз.

Аналитиктің портфолио репозиторийі

cafe-analysis/
├── README.md          ← ең маңызды файл
├── sql/               ← сұраулар
├── notebooks/         ← pandas талдау
├── dashboard/         ← Power BI скриншоттары
└── data/              ← шағын үлгі деректер

README құрылымы: бизнес сұрақ → деректер → әдіс → негізгі нәтижелер (сандармен) → ұсыныс → қалай іске қосу. Жұмыс беруші алдымен README-ді оқиды.

Жақсы README мысалы

# Кофехана желісі: жарнама бюджетін қайта бөлу

**Нәтиже:** referral арнасының клиенттері 2 есе жиі қайта келеді.
Бюджеттің 20%-ын Instagram-нан referral-ға көшіруді ұсынамын.

## Деректер
6 айлық тапсырыстар (2 400 жол), клиенттер (40 жол).

## Әдіс
SQL: тазалау, айлық метрикалар, арна сегменттері, retention.
Python: ROAS есебі.

## Қалай іске қосу
sql/ папкасындағы файлдарды ретімен орындаңыз.

Мысалдағы сандар шартты. Маңыздысы — құрылым: нәтиже бірінші, әдіс қысқа, іске қосу нұсқаулығы соңында.

Деректі репозиторийге салу

Нақты клиенттердің деректерін ешқашан ашық репозиторийге салмаңыз. Оның орнына жасанды (synthetic) немесе анонимделген шағын үлгіні қолданыңыз да, README-де соны жазыңыз.
