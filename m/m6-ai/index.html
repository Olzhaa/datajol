AIE AI Engineering: AI Engineering қазақша: RAG сапасы, ReAct агент, guardrails, LLM сервисі

GenAI модулінде LLM қолданбасының негізгі бөліктерін құрдыңыз: prompt, RAG, function calling, агент. Енді инженер көзімен тереңірек қараймыз: модель token-ді қалай таңдайды, генерацияны қалай басқарамыз, құн мен latency-ді қалай есептейміз, RAG сапасын қалай өлшейміз, агент пен сервисті өндіріске қалай шығарамыз. Браузерде шын модель жоқ, сондықтан бәрін таза Python симуляциясымен жасаймыз: сценарий бойынша жауап беретін fake LLM, қолдан жазылған logits және шағын embedding векторлары.

1. LLM ішінде: token, logits, softmax, келесі token циклі

GenAI модулінде LLM «келесі token-ді болжайды» деп айттық. Енді осы сөйлемнің ішіне кіреміз: модельдің шығысы қандай сандар, олар қалай ықтималдыққа айналады және ұзын жауап қандай циклмен жазылады.

Token-нен logits-ке дейін

Tokenizer мәтінді token-дерге бөледі, әр token-нің сөздіктегі нөмірі (id) бар. Модель осы id тізбегін алып, сөздіктегі әр token үшін бір сан қайтарады. Бұл сандар logits деп аталады: олар кез келген нақты сан болуы мүмкін (теріс те), қосындысы 1 емес. Сөздік 100 000 token болса, әр қадамда 100 000 logit шығады.

Softmax: logits-ті ықтималдыққа айналдыру

Softmax әр logit-ті exp арқылы оң санға айналдырып, бәрінің қосындысына бөледі. Нәтижеде барлық ықтималдық 0 мен 1 арасында, қосындысы 1.

import math

def softmax(logits):
    m = max(logits.values())                 # тұрақтылық үшін
    exps = {t: math.exp(v - m) for t, v in logits.items()}
    total = sum(exps.values())
    return {t: e / total for t, e in exps.items()}

print(softmax({"латте": 2.0, "капучино": 1.0, "шай": 0.0}))
# {'латте': 0.665, 'капучино': 0.245, 'шай': 0.090}

Неге max-ты аламыз? math.exp(1000) OverflowError береді. Барлық logit-тен бірдей санды алу нәтижені өзгертпейді (бөлшектің алымы мен бөлімі бірдей көбейткішке қысқарады), бірақ сандар қауіпсіз аймақта қалады.

Келесі token циклі (autoregressive)

  1. Контекстті модельге беріп, logits аламыз.
  2. Logits-тен бір token таңдаймыз (greedy: ең үлкенін; sampling: ықтималдықпен).
  3. Token-ді контекстке қосамыз.
  4. Арнайы <eos> (end of sequence) token шықса немесе max_tokens шегіне жетсек, тоқтаймыз.

Әр жаңа token үшін модель бүкіл есептеуді қайталайды, сондықтан output token-дері input-тан қымбат әрі баяу. Жауап 500 token болса, бұл 500 рет қайталанатын цикл.

Context window

Модель бір рет көре алатын token саны шектеулі: prompt пен жауап бірге осы терезеге сыюы керек. 128K терезе болса және 4K жауап күтсек, prompt-қа 124K қалады. Терезеден асқанын модель мүлдем көрмейді: ол «ұмытпайды», оған жай берілмейді.

Perplexity: модель қаншалық «таңданды»

Мәтіннің әр token-іне модель берген ықтималдықтарды алып, exp(-орташа log p) есептесек, perplexity шығады. Ол 1-ге жақын болса, модель мәтінді сенімді болжаған; үлкен болса, мәтін модель үшін «күтпеген». Бұл тілдік модельдерді салыстырудың классикалық метрикасы.

Жиі қателер

  • Logits-ті ықтималдық деп қабылдау: оларды тек softmax-тан кейін салыстыруға болады.
  • Softmax-ты max-сыз жазу: үлкен logit-те overflow болады.
  • <eos> token-ін жауап мәтініне қосып жіберу.
Greedy decode үшін softmax міндетті емес: logits-тің ең үлкені ықтималдықтың да ең үлкені. Softmax sampling, top-p және ықтималдықты көрсету үшін керек.

2. Генерацияны басқару: temperature, top-k, top-p, penalty, stop

GenAI модулінде temperature-ді «шығармашылық тұтқасы» ретінде қолдандық. Енді ол және оның серіктері logits пен ықтималдыққа нақты не істейтінін көреміз. Провайдерлердің API-інде бұлар жай параметр, бірақ ішінде бәрі бірнеше жол Python.

Temperature

Softmax алдында әр logit-ті T-ға бөлеміз: softmax(logit / T). T < 1 үлестірімді «өткір» етеді (ең ықтималы одан да ықтимал), T > 1 «тегістейді». T = 0 іс жүзінде greedy: әрқашан ең үлкені.

Top-k және top-p (nucleus)

  • Top-k: ең ықтимал k token-ді қалдырып, қалғанын өшіреміз, сосын қайта қалыпқа келтіреміз (қосынды 1 болсын).
  • Top-p: token-дерді ықтималдығы бойынша кемуі ретімен тізіп, жинақталған қосынды p-ге жеткенше аламыз. Модель сенімді болса, 1-2 token қалады; сенімсіз болса, көп token қалады. Яғни top-p өзі бейімделеді.
probs = {"кофе": 0.5, "шай": 0.3, "су": 0.15, "шырын": 0.05}
# top_k=2  → {"кофе": 0.625, "шай": 0.375}
# top_p=0.9 → кофе (0.5) + шай (0.8) + су (0.95 ≥ 0.9)
#           → {"кофе": 0.526, "шай": 0.316, "су": 0.158}

Repetition penalty

Модель кейде бір сөзді қайталай береді. Жауапта бұрын шыққан token-дердің logit-ін әлсіретеміз: оң logit-ті penalty-ге бөлеміз, теріс logit-ті penalty-ге көбейтеміз (екі жағдайда да ол кішірейеді). OpenAI-стильдегі API-де ұқсас идея presence_penalty және frequency_penalty деп аталады: олар logit-тен тұрақты сан немесе қайталану санына пропорционал сан алады.

max_tokens, stop sequences, seed

  • max_tokens: жауаптың ұзындық шегі. Шекке жетсе, жауап сөйлемнің ортасында үзіледі (finish_reason = "length").
  • Stop sequences: осы жол пайда болса, генерация тоқтайды, ал жолдың өзі жауапқа кірмейді. Мысалы, "\nПайдаланушы:" модельдің пайдаланушы атынан жазып кетуін тоқтатады.
  • Seed: sampling кездейсоқ сандарға сүйенеді. Seed бекітілсе, бірдей сұрау бірдей жауап береді (көп провайдер мұны «мүмкіндігінше» деп уәде етеді).
import random
rng = random.Random(42)     # бекітілген seed
def sample(probs, rng):
    r = rng.random()
    acc = 0.0
    for tok, p in sorted(probs.items(), key=lambda kv: -kv[1]):
        acc += p
        if r < acc:
            return tok
    return tok

Әдеттегі тізбек

penalty → temperature → softmax → top-k → top-p → қайта қалыпқа келтіру → sample → stop тексеру. Бұл ретті шатастырсаңыз, параметрлер күткендей әсер етпейді.

Жиі қателер

  • Сүзгіден кейін қайта қалыпқа келтіруді ұмыту: қосынды 1-ден кіші болып қалады.
  • Temperature мен top-p-ны бір уақытта қатты өзгерту: әсерлерін ажырату қиын. Біреуін ғана реттеген дұрыс.
  • JSON немесе жіктеу тапсырмасында жоғары temperature қою.
Детерминистік тапсырмада (экстракция, жіктеу) temperature 0 және бекітілген seed; мәтін жазуда temperature 0.7 шамасы және top-p 0.9. Әр өзгерісті eval жиынында тексеріңіз.

3. Ұзын контекст және құн

GenAI модулінде тарихты token бюджетіне сыйғыздық және бір сұраудың құнын есептедік. Өндірісте сұрақ басқаша қойылады: «контекстке не кіргізсек, сапа жоғары, құн төмен болады?» Ұзын контекст тегін емес: input token-дерге ақша төлейміз, latency өседі, ал модель ортадағы ақпаратты нашар пайдаланады.

Token бюджеті

Бюджет = context window − күтілетін жауап (max_tokens) − system prompt − құралдар сипаттамасы. Қалғаны тарих пен RAG үзінділеріне бөлінеді. Әр бөлікке алдын ала үлес беріңіз: мысалы, тарихқа 30%, үзінділерге 60%.

Lost in the middle

Зерттеулер көрсеткендей, модельдер ұзын контекстің басы мен соңындағы ақпаратты жақсы, ал ортасындағыны нашар пайдаланады. Практикалық салдары: ең маңызды үзінділерді шетке қойыңыз. Ең релевантты chunk бірінші, екіншісі соңғы, үшіншісі екінші орында, тағы сол сияқты; ең әлсіздері ортада қалады.

chunks = ["A", "B", "C", "D", "E"]   # релевантты бойынша кему
# шеттерге орналастыру → ["A", "C", "E", "D", "B"]

Құн және prompt caching

Көп провайдер бірдей префиксті (system prompt, құралдар, тұрақты құжаттар) кэштейді, ал кэштен оқылған input token-дер әлдеқайда арзан, мысалы, бағаның 10%-ы. Сондықтан prompt-тың тұрақты бөлігін басына, өзгеретін бөлігін (пайдаланушы сұрағы) соңына қойыңыз.

uncached = 500 * 0.40 / 1_000_000      # $0.40 / 1M input
cached   = 1500 * 0.04 / 1_000_000     # кэштелген: 10%
output   = 200 * 1.60 / 1_000_000      # $1.60 / 1M output
per_request = uncached + cached + output   # $0.00058

Модельді құн мен сапа бойынша таңдау

Бір сұраудың бағасы аз модель әрқашан арзан емес. Маңыздысы: бір дұрыс жауаптың құны = сұрау құны / accuracy. Арзан модель жиі қателессе, қате жауаптарды оператор түзетеді, ол да ақша. Алдымен сапа шегін қойыңыз (мысалы, accuracy ≥ 0.85), сосын шектен өткендердің ішінен бір дұрыс жауабы ең арзанын таңдаңыз.

Жиі қателер

  • «Context window 1M, бәрін сала береміз»: құн мен latency өседі, сапа көбіне төмендейді.
  • Өзгермелі мәтінді (күн, уақыт, пайдаланушы аты) system prompt-тың басына қою: кэш жұмыс істемейді.
  • Rolling summary-ді тексермеу: қысқаша мазмұнда тапсырыс нөмірі сияқты маңызды дерек сақталуы керек.
Әр сұрауда input, cached және output token санын логқа жазыңыз. Айлық шотты болжаудың ең сенімді жолы: нақты трафиктің бір күнін алып, 30-ға көбейту.

4. Inference: latency, batching, KV-cache, кэш

Пайдаланушы үшін модельдің ақылы ғана емес, жылдамдығы да маңызды. Бұл сабақта модель жауапты қалай «шығаратынын» (inference) және оны қалай тездетіп, арзандататынымызды көреміз.

Екі кезең: prefill және decode

  • Prefill: модель бүкіл prompt-ты бір рет параллель өңдейді. Prompt ұзын болса, бұл кезең ұзарады.
  • Decode: жауап token-ден token-ге жазылады (1-сабақтағы цикл). Әр қадам алдыңғысын күтеді, сондықтан параллельдеу қиын.

Осыдан екі негізгі метрика шығады: TTFT (time to first token, бірінші token-ге дейінгі уақыт) және tokens/sec (decode жылдамдығы). Жалпы уақыт ≈ TTFT + output_tokens / tokens_per_sec. TTFT 400 мс, жылдамдық 50 token/с, жауап 300 token болса: 0.4 + 6 = 6.4 секунд. Streaming жалпы уақытты азайтпайды, бірақ пайдаланушы 0.4 секундта мәтінді көре бастайды.

KV-cache

Әр жаңа token үшін attention алдыңғы барлық token-дердің key және value векторларын қажет етеді. Оларды әр қадамда қайта есептемеу үшін жадта сақтайды: бұл KV-cache. Ол decode-ты қатты тездетеді, бірақ GPU жадын жейді: ұзын контекст пен көп қатар сұрау жадқа сыймай қалуы мүмкін.

Batching

GPU бір сұрауды өңдегенде толық жүктелмейді. Бірнеше сұрауды бірге (batch) өңдесек, бір секундтағы token саны (throughput) өседі. Continuous batching: бір сұрау біткенде оның орнына кезектегі жаңа сұрау бірден қосылады, бүкіл batch-тің бітуін күтпейді.

Quantization

Модель салмақтары әдетте 16 бит (fp16/bf16). Оларды 8 немесе 4 битке қысу жадты 2-4 есе азайтады, сапа сәл ғана төмендейді. Жад ≈ параметр саны × бит / 8: 7B модель fp16-да ≈ 14 GB, int4-те ≈ 3.5 GB (KV-cache бөлек).

Serving engines

  • vLLM: PagedAttention арқылы KV-cache-ті беттерге бөліп, жадты үнемдейді; continuous batching; OpenAI-үйлесімді API береді.
  • TGI, SGLang: ұқсас серверлер. llama.cpp және Ollama: ноутбук пен CPU-да quantized модельдер.

Бұлар браузерде жұмыс істемейді, бірақ архитектураны түсіну маңызды: өз модельді хостингке қойғанда, GPU құнын осылар анықтайды.

Бірдей сұрауларды кэштеу

Қолдау чатында «интернет баяу» деген сұрақ күніне жүздеген рет келеді. Prompt-ты қалыпқа келтіріп (бос орын, регистр), кілт ретінде қолдансақ, бірдей сұрауға модельді қайта шақырмаймыз. Шын жүйеде кілтке модель аты мен prompt нұсқасын да қосып, hashlib.sha256 арқылы қысқартады, ал жазбаға TTL (жарамдылық мерзімі) береді.

import re
def normalize(prompt):
    return re.sub(r"\s+", " ", prompt.strip().lower())
normalize("  Интернет   БАЯУ ")   # 'интернет баяу'

Latency-ді өлшеу: p50 және p95

Орташа мән алдайды: 99 сұрау 1 секунд, біреуі 60 секунд болса, орташа 1.6 с, ал бір клиент бір минут күтті. Сондықтан перцентиль қараймыз: p50 (медиана, қалыпты тәжірибе) және p95 (ең баяу 5%). Nearest-rank әдісі: сұрыптаймыз, rank = ceil(p × n / 100), мән = sorted[rank - 1].

Жиі қателер

  • Тек орташа latency-ді бақылау.
  • Кэш кілтіне модель атын қоспау: модель ауысқанда ескі жауаптар қайтарылады.
  • Жеке деректі (тапсырыс, телефон) бар жауаптарды ортақ кэшке салу.
Чатта TTFT-ты, ал фондық тапсырмада (мыңдаған құжатты жіктеу) throughput-ты оңтайландырыңыз. Фондық тапсырмаға провайдерлердің арзан batch API-і бар.

5. Векторлық іздеу тереңірек: ANN, hybrid search, reranking

GenAI модулінде cosine similarity арқылы top-k іздеуді жаздық. Ол бірнеше мың құжатқа жетеді. Миллион chunk болғанда немесе сұрауда нақты код (тариф атауы, қате нөмірі) кездескенде басқа құралдар керек.

Cosine, dot product және нормализация

Cosine = dot(a, b) / (|a| · |b|). Егер барлық векторды алдын ала ұзындығы 1 болатындай нормаласақ, cosine кәдімгі dot product-қа айналады: бөлу керек емес. Сондықтан векторлық базалар векторды индекске салғанда бір рет нормалайды, ал іздеуде тек dot есептейді. Кейбір embedding модельдері нормаланған вектор қайтарады; құжатын оқыңыз.

import math
def normalize(v):
    n = math.sqrt(sum(x * x for x in v))
    return [x / n for x in v]

normalize([3, 4])   # [0.6, 0.8]

Brute force және ANN

Brute force әр сұрауда барлық N векторды салыстырады: O(N·d). Дәл, бірақ миллиондаған векторда баяу. ANN (approximate nearest neighbors) индекстері сәл дәлдікті жылдамдыққа айырбастайды:

  • IVF: векторларды алдын ала кластерлерге бөледі (k-means). Іздеуде сұрауға ең жақын nprobe кластерді ғана тексереді. nprobe көп болса, дәлірек, бірақ баяу.
  • HNSW: векторлардан көп деңгейлі граф құрады. Жоғарғы сирек деңгейде «ұзын секірістер», төменгі деңгейде жақын көршілер. Іздеу графпен жүріп, жақындай береді. Жылдам және дәл, бірақ жадты көп алады.

ANN сапасы recall-мен өлшенеді: ANN тапқан top-10 ішінде шын top-10-ның қаншасы бар.

Hybrid search

Embedding мағынаны жақсы ұстайды, бірақ «Турбо-500» тарифі немесе «E-651» қате коды сияқты нақты сөздерді жіберіп алуы мүмкін. Keyword іздеу (BM25) керісінше. Екеуін біріктіреміз. BM25-тің жеңілдетілген түрі:

idf(t)   = log(1 + (N - df + 0.5) / (df + 0.5))
score(d) = Σ idf(t) · tf · (k1 + 1) / (tf + k1)    # k1 ≈ 1.5

Мұнда df сөз кездесетін құжат саны, tf құжаттағы сөз саны. Сирек сөз көп ұпай береді, ал бір сөздің қайталануы ұпайды шексіз өсірмейді (saturation).

Екі тізімді біріктірудің қарапайым әрі сенімді тәсілі: Reciprocal Rank Fusion (RRF). Әр құжат әр тізімдегі орнына қарай 1 / (60 + rank) ұпай алады, ұпайлар қосылады. Сандардың шкаласы әртүрлі болса да жұмыс істейді, себебі тек орынды қолданады.

Reranking

Бірінші кезең (bi-encoder немесе BM25) 50 кандидатты тез табады. Екінші кезеңде cross-encoder reranker әр (сұрақ, chunk) жұбын бірге оқып, дәлірек ұпай береді, біз top-5-ін LLM-ге жібереміз. Reranker баяу, сондықтан тек кандидаттарға қолданылады.

Жиі қателер

  • Нормаланбаған векторларда dot product қолдану: ұзын вектор әрқашан «ұқсас» болып шығады.
  • Индекс пен сұрауды әртүрлі embedding моделімен жасау.
  • Тек векторлық іздеуге сену: кодтар мен атаулар бар доменде hybrid міндетті.
Алдымен brute force және шағын eval жиынымен бастаңыз. ANN индексін тек latency шынымен мәселе болғанда қосыңыз және оның recall-ын brute force нәтижесімен салыстырыңыз.

6. RAG сапасын бағалау: recall@k, MRR, faithfulness

RAG-ты «көзбен» тексеру ең жиі кездесетін қате: бес сұрақ қойып, жауаптар жақсы көрінсе, дайын деп есептейміз. Өндірісте chunk өлшемін, embedding моделін немесе prompt-ты өзгерткен сайын сапа сандармен өлшенуі керек. Ол үшін RAG-ты екі бөлек бөлікке бөліп бағалаймыз: retrieval және generation.

Golden question set

Бұл сұрақтар мен оларға жауап беретін chunk id-лерінің тізімі. Оны құжатты білетін адам (қолдау операторы) жасайды. 30-50 сұрақ бастауға жетеді.

GOLDEN = [
    {"q": "Роутер жанбаса не істеймін?",  "relevant": {"faq1"}},
    {"q": "Kaspi арқылы төлеуге бола ма?", "relevant": {"faq4"}},
    {"q": "Тарифті қалай өзгертемін?",     "relevant": {"faq2", "faq7"}},
    {"q": "Ұшақ билеті қанша тұрады?",     "relevant": set()},   # жауабы жоқ
]

Жауабы жоқ сұрақтарды да қосыңыз: жүйе «білмеймін» дей ала ма, соны тексереді.

Retrieval метрикалары

  • recall@k: релевантты chunk-тардың қандай үлесі top-k ішіне түсті. Retrieved = [faq7, faq3, faq2], relevant = {faq2, faq7}, k = 3: recall@3 = 2/2 = 1.0. k = 1 болса: 1/2 = 0.5.
  • MRR (mean reciprocal rank): бірінші релевантты chunk қай орында. 1-орын → 1, 2-орын → 0.5, 3-орын → 0.33, табылмаса 0. Барлық сұрақ бойынша орташа.
  • Hit rate@k: кемінде бір релевантты chunk top-k-да ма.

Recall төмен болса, LLM-ді немесе prompt-ты түзетудің мәні жоқ: модель керекті ақпаратты көрмеді.

Generation: faithfulness

Жауаптың әр тұжырымы берілген контекстке сүйене ме? Қатаң әрі арзан тексеріс: модельден әр сөйлемнен кейін [faq3] түрінде дерек көзін жазуды талап етіп, кодпен тексереміз:

  1. Жауапты сөйлемдерге бөлеміз.
  2. Әр сөйлемде кемінде бір citation бар ма?
  3. Әр citation шынымен retrieved chunk-тардың бірі ме (модель жоқ id ойлап таппады ма)?
import re
sentences = re.split(r"(?<=[.!?])\s+", answer.strip())
cites = re.findall(r"\[([\w-]+)\]", sentence)

Бұл тексеріс тұжырымның мағынасы chunk-қа сай ма, оны білмейді. Ол үшін LLM-as-judge керек (11-сабақ). Бірақ citation жоқ немесе жалған citation бар сөйлемдерді бірден ұстайды.

Chunk size эксперименті

Бір golden жиынында бірнеше конфигурацияны салыстырыңыз: chunk 200, 400, 800 token. Әрқайсысы үшін recall@k есептеп, кестеге жазыңыз. Тең нәтижеде кішісін таңдаңыз: ол prompt-қа аз token қосады, демек арзан әрі жылдам.

Chunkrecall@3MRRPrompt token
2000.720.61~700
4000.860.74~1300
8000.860.70~2500

Жиі қателер

  • Golden жиынды бір рет жасап, ешқашан толықтырмау. Өнімдегі сәтсіз сұрақтарды жиынға қосып отырыңыз.
  • Тек соңғы жауапты бағалау: қате retrieval-дан ба, generation-нан ба, белгісіз қалады.
  • Бір метрикаға ғана қарау: recall жоғары, бірақ MRR төмен болса, дұрыс chunk соңғы орындарда.
Eval-ды CI-ға қосыңыз: chunk өлшемін немесе embedding моделін өзгертетін әр pull request recall@k мен faithfulness кестесін шығарсын. Сан төмендесе, merge жасалмайды.

7. ReAct агент: Thought, Action, Observation

GenAI модулінде агент циклін JSON құрал-шақыруларымен жаздық. Енді дәл сол идеяның классикалық мәтіндік түрін, ReAct-ты (Reason + Act) толық құрамыз: модель ойын жазады, әрекет таңдайды, біз әрекетті орындап, нәтижені қайтарамыз. Мәтіндік форматты түсіну пайдалы: function calling жоқ шағын open-source модельдерде, сондай-ақ агент логын оқығанда дәл осы құрылым кездеседі.

Формат

Question: А-1024 тапсырысының 3 данасы қанша тұрады?
Thought: Алдымен тапсырыстың бағасын білу керек.
Action: order_lookup[А-1024]
Observation: латте, 1450 ₸
Thought: Енді 3-ке көбейтемін.
Action: calculator[1450*3]
Observation: 4350
Thought: Жауап дайын.
Final Answer: 3 латте 4350 ₸ тұрады.

Модель Thought және Action жолдарын жазады. Observation жолын біз жазамыз: құралды орындап, нәтижесін транскриптке қосып, модельді қайта шақырамыз.

Цикл

  1. Транскрипт (сұрақ + бұрынғы қадамдар) модельге беріледі.
  2. Модельдің жауабын талдаймыз (parsing): Final Answer болса, тоқтаймыз; Action: tool[input] болса, құралды орындаймыз.
  3. Observation: ... жолын қосып, 1-қадамға ораламыз.
  4. max_steps шегінен асса, тоқтап, «жауап табылмады» дейміз.

Action-ды талдау

import re
m = re.search(r"Action:\s*(\w+)\[(.*?)\]", text)
if m:
    tool, arg = m.group(1), m.group(2)

Модель форматты бұзуы мүмкін: Action: calculator(2+2) немесе мүлдем Action жоқ. Мұндай жағдайда үнсіз құламаймыз, Observation ретінде түзету нұсқауын қайтарамыз: «Формат қате: Action: tool[input] немесе Final Answer: ... жазыңыз». Көбіне модель келесі қадамда түзеледі.

Stop sequence маңызы

Модель Action жазғаннан кейін Observation-ды да өзі ойдан жалғастырып кетуі мүмкін: «Observation: 5000 ₸». Сондықтан шын жүйеде stop=["\nObservation:"] қоямыз (2-сабақ): модель Action-нан кейін тоқтайды, ал Observation-ды тек құрал жазады.

Құралдар қауіпсіз болуы керек

Калькулятор үшін eval өте ыңғайлы, бірақ модель (немесе prompt injection) __import__("os") жазуы мүмкін. Сондықтан алдымен кіріс тек цифр, амал белгілері, жақша мен бос орыннан тұратынын тексереміз, тек содан кейін есептейміз. Тапсырысты іздеу құралы тек оқиды, ештеңе өзгертпейді.

ALLOWED = re.compile(r"[0-9+\-*/(). ]+")
if not ALLOWED.fullmatch(expr):
    return "Қате: рұқсат етілмеген таңба"

Сынау: scripted fake LLM

Агентті шын модельсіз тексеру үшін алдын ала жазылған жауаптарды кезекпен қайтаратын fake LLM қолданамыз. Ол модельге қандай транскрипт келгенін де сақтайды, сондықтан Observation дұрыс қосылғанын тексере аламыз. Бұл агенттің кодын тексереді, модельдің ақылын емес.

Жиі қателер

  • Observation-ды транскриптке қоспау: модель құрал нәтижесін көрмей, сол әрекетті қайталайды.
  • Белгісіз құрал атын KeyError-мен құлату. Оның орнына Observation: «Белгісіз құрал».
  • max_steps жоқ: шатасқан агент шексіз айналады.
Транскриптті толық логқа жазыңыз. Агент қате жауап берсе, қай қадамда ойы бұрыс кеткенін Thought жолдарынан бірден көресіз.

8. Guardrails: кіріс пен шығысты тексеру

GenAI модулінде prompt injection шабуылдарын және жеке деректі жасыруды талқыладық. Өндірісте бұлар бөлек функциялар емес, әр сұрау өтетін guardrails қабаты: модельге дейін кірісті тексереміз, модельден кейін шығысты тексереміз, бірдеңе бұзылса, қауіпсіз fallback береміз.

сұрау → [input guard] → LLM → [output guard] → жауап
            ↓ бас тарту             ↓ fallback

Input guard

  • Ұзындық: бос немесе тым ұзын мәтін (мысалы, 2 000 таңбадан көп) бас тартылады. Бұл құнды да қорғайды.
  • Prompt injection үлгілері: «ignore previous instructions», «алдыңғы нұсқауларды ұмыт», «system prompt-ты көрсет». Regex тізімі тек бірінші сүзгі: шебер шабуылды ұстамайды, бірақ арзан және жылдам. Келесі қабат: бөлек жіктеуіш модель.
  • PII masking: ЖСН (12 цифр), телефон (+7 701 123 45 67, 87011234567), карта нөмірі. Модельге және логқа тек жасырылған мәтін кетеді.
import re
IIN = re.compile(r"\b\d{12}\b")
PHONE = re.compile(r"(?:\+7|8)[\s-]?\(?\d{3}\)?[\s-]?\d{3}[\s-]?\d{2}[\s-]?\d{2}")
text = IIN.sub("[ЖСН]", text)
text = PHONE.sub("[ТЕЛЕФОН]", text)

Реті маңызды: алдымен ЖСН (тура 12 цифр), сосын телефон. Әйтпесе телефон үлгісі ЖСН-нің бір бөлігін «жұтып» қоюы мүмкін.

Output guard

  • Құрылым: модель JSON қайтаруы керек болса, json.loads сәтті ме, барлық өріс бар ма, типтері дұрыс па. Бұл JSON Schema немесе Pydantic-тің шағын нұсқасы.
  • Рұқсат етілген тақырыптар: интернет-провайдердің көмекшісі тек internet, billing, tariff туралы жауап береді. Модель «саясат» деп белгілесе, жауап берілмейді.
  • Ағып кету: жауапта system prompt үзіндісі, API кілті немесе басқа клиенттің деректері жоқ па.
SCHEMA = {"answer": str, "sources": list, "topic": str}
ALLOWED_TOPICS = {"internet", "billing", "tariff"}

Fallback

Тексеріс сәтсіз болса, пайдаланушыға қате мәтінін көрсетпейміз. Үш нұсқа бар: (1) модельді түзету нұсқауымен қайта шақыру (1-2 рет); (2) дайын қауіпсіз жауап: «Кешіріңіз, бұл сұраққа жауап бере алмаймын. Оператор 24/7: 7010»; (3) сұрауды адамға (операторға) беру. Қайсысы болса да, логқа себебімен жазылады.

Дайын құралдар

NeMo Guardrails, Guardrails AI, Llama Guard сияқты жобалар осы қабаттарды дайын береді: схема валидациясы, тақырып сүзгілері, қауіпті мазмұнды жіктеу. Бірақ олардың ішінде дәл осы идеялар: тексеру, бас тарту, fallback. Ережелерді өз доменіңізге бейімдеу бәрібір сіздің жұмысыңыз.

Жиі қателер

  • Тек input-ты тексеру: модель шығысы да қауіпті болуы мүмкін (жалған сілтеме, құпия).
  • PII-ді модельге жасырып, логқа ашық жазу.
  • Guard-тың әр бас тартуын пайдаланушыға «injection анықталды» деп көрсету: шабуылдаушыға қай ереже жұмыс істегенін айтпаңыз.
  • Guardrail-дардың өзін тестілемеу: жалған бас тартулар (false positive) да пайдаланушыны ренжітеді.
Әр guard үшін екі тест жиыны ұстаңыз: ұсталуы керек мысалдар және өтуі керек қалыпты сұраулар. Ережені өзгерткенде екеуін де тексеріңіз.

9. Оркестрация және көп агентті жүйелер

Нақты LLM қолданбасы бір шақырудан тұрмайды: сұрауды жіктеу, іздеу, жауап жазу, тексеру, қажет болса қайталау. Осы қадамдарды қалай байланыстыратынымыз оркестрация деп аталады. Екі негізгі тәсіл бар: қатаң pipeline (граф, state machine) және өз бетінше шешетін агенттер.

Граф ретінде pipeline

LangGraph сияқты құралдардың идеясы қарапайым: жүйе түйіндерден (node) және қырлардан (edge) тұрады. Барлық түйін бір ортақ state сөздігін оқып, оған өз нәтижесін қосады. Қыр не тұрақты (A-дан кейін әрқашан B), не шартты (state-ке қарап келесі түйінді таңдайтын функция). Арнайы END түйіні жұмысты аяқтайды.

def classify(state):  return {"intent": "tech"}
def retrieve(state):  return {"docs": ["faq3"]}
def answer(state):    return {"answer": "Роутерді қайта қосыңыз [faq3]"}

NODES = {"classify": classify, "retrieve": retrieve, "answer": answer}
EDGES = {
    "classify": lambda s: "retrieve" if s["intent"] != "chitchat" else "answer",
    "retrieve": "answer",
    "answer": "END",
}

Неге бұл тиімді? Әр қадам бөлек тестіленеді, логта қай түйіннен өткені көрінеді, ал шартты қырлар «жауап тексерістен өтпесе, қайта жаз» сияқты циклдерді анық сипаттайды. Циклдер болғандықтан, мұнда да қадам шегі міндетті.

Router: сұрауды маманға жіберу

Көп агентті жүйенің ең қарапайым әрі пайдалы түрі: router сұрауды жіктеп, оны маман агентке жібереді. Интернет-провайдерде: billing (төлем, шот), tech (роутер, жылдамдық), sales (тариф, қосылу). Әр маманның өз system prompt-ы, өз құралдары және өз құжаттары бар. Router арзан модель немесе тіпті кілт сөз ережелері болуы мүмкін; сенімсіз болса, жалпы (general) агентке береді.

Басқа үлгілер

  • Planner / executor: бір агент жоспар жазады, басқалары қадамдарды орындайды.
  • Generator / critic: бірі жауап жазады, екіншісі критерий бойынша тексереді, сәтсіз болса қайта жаздырады.
  • Parallel: бірнеше маман бір уақытта жұмыс істеп, нәтижелер біріктіріледі.

Retries

LLM қадамы кейде сәтсіз болады: JSON бұзылады, тексерістен өтпейді. Pipeline-да әр осындай түйінге шағын retry саясатын береміз: нәтижені тексеріп, сәтсіз болса 2-3 рет қайталау, сосын fallback. Желі қателеріне арналған backoff келесі сабақта.

Қашан көп агент керек емес

Әр агент: қосымша LLM шақыруы, latency, құн және жаңа қате көзі. Көп жағдайда жақсы құрылған бір pipeline (router + RAG + тексеріс) бірнеше «сөйлесетін» агенттен сенімдірек. Агенттерді тапсырма шынымен ашық болғанда (қадамдар саны мен реті алдын ала белгісіз) қолданыңыз.

Жиі қателер

  • Түйіндер state-ті толық ауыстырады: басқа түйіндердің нәтижесі жоғалады. Тек жаңа кілттерді қосыңыз.
  • Шартты қыр жоқ түйін атын қайтарады: граф құлайды. Атауларды тексеріңіз.
  • Router-дің қате жіктеуін бағаламау: оған да eval жиыны керек.
Графтың өтілген жолын (path) әр сұрауда логқа жазыңыз: «classify → retrieve → answer → check → answer». Бұл агенттің ойын түсінудің ең жылдам жолы.

10. LLM сервисін өндіріске шығару

Notebook-та жұмыс істейтін RAG көмекшісін мобильді қосымша немесе сайт шақыратын сервиске айналдыру керек. Бұл сабақта сервистің пішінін, сенімділік тәсілдерін және бақылауды қарастырамыз. Веб-сервер браузерде іске қоспаймыз, сондықтан код мәтін ретінде беріледі, ал жаттығуларда сервистің логикасын fake сағатпен (fake clock) сынаймыз.

Endpoint пішіні

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ChatRequest(BaseModel):
    session_id: str
    message: str

class ChatResponse(BaseModel):
    answer: str
    sources: list[str]
    request_id: str

@app.post("/v1/chat", response_model=ChatResponse)
async def chat(req: ChatRequest):
    guard = input_guard(req.message)
    if not guard["allowed"]:
        return ChatResponse(answer=FALLBACK, sources=[], request_id=new_id())
    reply = await llm_client.generate(build_prompt(guard["text"]), timeout=20)
    return ChatResponse(**parse_reply(reply), request_id=new_id())

Pydantic кіріс пен шығыстың схемасын тексереді, ал /v1/ нұсқасы API-ді клиенттерді бұзбай өзгертуге мүмкіндік береді.

Async және streaming

LLM-ге сұрау секундтар алады, ал осы уақыт ішінде сервер тек күтеді (желі I/O). async def және await бір процеске күту кезінде басқа сұрауларға қызмет етуге мүмкіндік береді: жүздеген чат бір уақытта. Streaming кезінде жауапты бөліктермен жібереміз, көбіне Server-Sent Events (SSE) форматында: әр бөлік data: ... жолы және бос жол, соңында data: [DONE].

data: {"delta": "Роутерді"}

data: {"delta": " қайта қосыңыз"}

data: [DONE]

Timeout, retry және backoff

Провайдер API-і кейде баяулайды немесе 429 (rate limit), 503 қайтарады. Ережелер: (1) әр шақыруда timeout болсын; (2) уақытша қателерде (timeout, 429, 5xx) қайталаймыз, ал 400 (сұрау қате) және 401 (кілт қате) қайталанбайды; (3) кідіріс экспоненциалды өседі: 0.5, 1, 2 секунд, көбіне кездейсоқ jitter қосылады, әйтпесе мың клиент бір сәтте қайта ұрады; (4) қайталау саны шектеулі.

Уақытқа тәуелді кодты тестілеу үшін нақты time.sleep орнына сағатты инъекциялаймыз: функция clock.sleep(d) шақырады, ал тестте fake сағат тек уақытты жазып алады. Тест бір миллисекундта өтеді.

Rate limit

Өз сервисіңізді де қорғау керек: бір пайдаланушы минутына мың сұрау жіберсе, бүкіл бюджет кетеді. Классикалық алгоритм token bucket: себетте ең көбі capacity белгі бар, ол секундына rate белгімен толады; әр сұрау бір белгі алады, белгі жоқ болса, 429 қайтарамыз.

Мониторинг

  • Prometheus метрикаларды жинайды: counter (сұрау саны, қате саны), histogram (latency, token саны), gauge (кезектегі сұраулар). Grafana оларды графикке салып, alert жібереді: «p95 latency 10 с-тан асты».
  • Tracing: бір сұраудың ішіндегі әр қадам (guard, retrieval, LLM, тексеріс) уақытымен және кірісімен жазылады. LangSmith, Langfuse, OpenTelemetry осыған арналған. Пайдаланушы «қате жауап» десе, request_id бойынша бүкіл трассаны ашасыз.
  • LLM-ге тән метрикалар: input/output token, құн, cache hit rate, fallback үлесі, пайдаланушы бағасы.

Жиі қателер

  • Timeout қоймау: бір ілініп қалған сұрау worker-ді мәңгі ұстайды.
  • Барлық қатені қайталау, оның ішінде 400: ақша мен уақыт босқа кетеді.
  • Async функцияның ішінде синхрон, баяу кітапхана шақыру: бүкіл сервер тоқтайды.
  • Логқа пайдаланушы мәтінін PII-сіз жазуды ұмыту (8-сабақ).
Әр жауапқа request_id қосыңыз және оны логта, трассада, пайдаланушы бағасында бірдей қолданыңыз. Сонда «осы жауап неге қате болды?» деген сұраққа бір минутта жауап табасыз.

11. Сапа, қауіпсіздік және fine-tuning

GenAI модулінде eval жиынын жасап, accuracy есептедік және fine-tuning қашан керек екенін талқыладық. Енді сапаны жүйелі түрде басқарамыз: offline және online бағалау, рубрикасы бар LLM-as-judge, prompt-тарға регрессия тесттері және fine-tuning деректерін дайындау.

Offline eval және online feedback

OfflineOnline
ҚашанШығарар алдында, CI-даӨнімде, нақты пайдаланушылармен
ДерекGolden жиын, тұрақты👍/👎, қайта сұрау, операторға өту үлесі
Не бередіҚайталанатын салыстыруШын сапа, жаңа сұрақ түрлері

Екеуі бір-бірін толықтырады: online-да сәтсіз болған сұрақтар offline жиынға қосылады. A/B тестте трафиктің бір бөлігі жаңа prompt-қа кетеді, ал метрикалар салыстырылады.

LLM-as-judge рубрикамен

«Жауап жақсы ма?» деп сұрау тұрақсыз баға береді. Оның орнына нақты критерийлер мен шкала береміз және жауапты қатаң форматта сұраймыз:

Жауапты бағала. Әр критерийге 1-ден 5-ке дейін.
Дәлдік: контекстке сай ма?
Толықтық: сұрақтың барлық бөлігіне жауап бар ма?
Сыпайылық: тон сыпайы ма?
Формат:
Дәлдік: X/5
Толықтық: X/5
Сыпайылық: X/5

Судья жауабын кодпен талдаймыз; формат бұзылса, бағаны жарамсыз деп есептейміз. Судьяның өзін тексеріңіз: 30-50 мысалда адам бағасымен сәйкестігін өлшеңіз. Белгілі ауытқулар: ұзын жауапқа жоғары баға беру, өз жауабын жоғары бағалау, бірінші тұрған нұсқаны таңдау.

Prompt регрессия тесттері

Prompt код сияқты: оны git-те сақтаймыз және әр өзгерісте тесттерді іске қосамыз. Ескі және жаңа нұсқаның нәтижесін мысал бойынша салыстырамыз: қайсысы бұзылды (regressed), қайсысы түзелді (fixed). Жалпы accuracy өссе де, маңызды мысал бұзылса, шығаруды тоқтатуға болады.

Prompt, RAG немесе fine-tuning?

  • Prompt: алдымен әрқашан осы. Арзан, жылдам, өзгерту оңай.
  • RAG: модельге жаңа немесе жеке білім керек (тарифтер, ережелер), ол жиі өзгереді, дерек көзін көрсету керек.
  • Fine-tuning: модельге тұрақты мінез-құлық керек: белгілі формат, стиль, домендік терминдер, немесе ұзын prompt-ты қысқарту арқылы құнды азайту. Fine-tuning жаңа фактілерді сенімді үйретпейді.

LoRA (Low-Rank Adaptation) модельдің барлық салмағын өзгертпейді: әр қабатқа екі шағын матрица қосып, тек соларды үйретеді. Үйретілетін параметрлер 0.1-1%, сондықтан бір GPU жеткілікті, ал адаптер файлы бірнеше MB. QLoRA бұған 4-биттік quantization қосады.

Fine-tuning деректері

Көп провайдер мен кітапхана JSONL форматын қабылдайды: әр жолда бір JSON, ішінде chat форматындағы messages.

{"messages": [{"role": "system", "content": "Сен Жылдам Нет көмекшісісің."}, {"role": "user", "content": "Роутер жанбайды"}, {"role": "assistant", "content": "Розетканы тексеріңіз..."}]}

Тексерілетіндер: әр жол жарамды JSON, messages бар, мазмұн бос емес, соңғы хабарлама assistant (модель осыны үйренеді). Сапа саннан маңызды: 300 мұқият тексерілген мысал 3 000 шулы мысалдан жақсы. Валидация жиынын бөлек ұстаңыз.

Жиі қателер

  • Судьяға рубрикасыз «1-ден 10-ға дейін баға бер» деу.
  • Fine-tuning-ті білім жаңарту үшін қолдану.
  • JSONL-да ensure_ascii ұмытылып, қазақ мәтіні \u04d9 болып кетуі: жарамды, бірақ тексеруге қолайсыз.
Қауіпсіздік тесттерін де регрессия жиынына қосыңыз: injection, жеке деректі сұрау, тақырыптан тыс сұрақтар. Жаңа prompt сапаны көтеріп, қорғанысты әлсіретуі мүмкін.

12. Қорытынды жоба: қолдау көмекшісі

Модульдің бөліктерін бір жүйеге жинаймыз. «Жылдам Нет» деген ойдан шығарылған интернет-провайдердің қолдау көмекшісі: FAQ құжаттарынан іздейді, кірісті тексереді, тек дерек көзімен жауап береді, ал сапасы golden жиында өлшенеді. Бәрі таза Python-да, модель орнына fake LLM.

Архитектура

сұрақ
  → guard: injection? → "blocked"
  → retrieve(top-2, min_score=1): ештеңе жоқ? → "no_answer" (LLM шақырылмайды)
  → build_prompt(контекст + сұрақ) → LLM
  → citation тексерісі: жоқ/жалған id? → "fallback"
  → "ok": жауап + sources

Әр тармақтың өз статусы бар. Бұл eval пен мониторингке қажет: «no_answer» үлесі өссе, FAQ-та жоқ тақырып пайда болды; «fallback» өссе, модель немесе prompt бұзылды.

1-қадам: retrieval

Embedding моделі жоқ болғандықтан, қарапайым кілт сөз іздеуін жасаймыз. Қазақ тілі жалғамалы: «роутер», «роутерді», «роутерге» бір сөз. Ең қарапайым «stemming»: сөздің алғашқы 5 әрпін алу. Бұл дөрекі тәсіл («төлем» мен «төлеу» сәйкес келмейді), бірақ жүйенің қаңқасын құруға жетеді, ал кейін оны 5-сабақтағы hybrid search-ке ауыстыруға болады. Stop-сөздерді («не», «қалай», «ма») алып тастаймыз.

def stems(text):
    words = re.findall(r"\w+", text.lower())
    return {w[:5] for w in words if w not in STOP and len(w) > 1}

Ұпай: сұрақ пен құжат stem-дерінің қиылысының өлшемі. min_score шегі маңызды: ол «ұшақ билеті» сияқты тақырыптан тыс сұраққа кездейсоқ құжат берілуін тоқтатады.

2-қадам: жауап және тексеріс

Prompt-та үзінділер [faq1] мәтін түрінде, ал нұсқауда әр сөйлемнен кейін дерек көзін жазу талап етіледі (6-сабақ). Модельдің жауабындағы барлық [id] шынымен берілген контексте бар ма, соны тексереміз. Жоқ id (мысалы, [faq99]) жалған дерек көзі, мұндай жауапты пайдаланушыға бермейміз.

3-қадам: golden жиында бағалау

Golden жиында төрт түрлі мысал болуы керек: қалыпты сұрақтар (күтілетін FAQ id), жауабы жоқ сұрақтар (күтілетін статус «no_answer»), шабуылдар (күтілетін статус «blocked») және «қиын» сұрақтар: синоним («модем» мен «роутер»), қате жазылған сөздер. Соңғылары жүйенің әлсіз жерін ашады. Eval нәтижесінде тек accuracy емес, сәтсіз сұрақтар тізімі де болуы керек: келесі жақсартуды солар көрсетеді.

Әрі қарай не істеуге болады

  • Кілт сөз іздеуін BM25 + embedding hybrid іздеумен ауыстыру, RRF арқылы біріктіру.
  • Синонимдер сөздігі («модем» → «роутер») немесе сұрақты LLM арқылы қайта жазу (query rewriting).
  • PII masking, rate limit, кэш және backoff қосу (8 және 10-сабақтар).
  • Әр сұраудың трассасын логқа жазу: статус, retrieved id, latency.

Жиі қателер

  • Retrieval ештеңе таппаса да модельді шақыру: модель ойдан жауап құрастырады.
  • Guard-ты retrieval-дан кейін қою: шабуыл мәтіні бәрібір өңделеді.
  • Golden жиынға тек жүйе жақсы жауап беретін сұрақтарды қосу.
Жүйені статустары бар функция ретінде жазыңыз: әр тармақ тестілеуге оңай, ал мониторингте әр статустың үлесі бірден көрінеді.

13. Модуль емтиханы: AI Engineering

Емтихан бүкіл модульді қамтиды: sampling және генерация параметрлері, контекст бюджеті мен lost in the middle, RAG метрикалары, сенімді шақыру (backoff және JSON тексерісі), өндірістік метрикалар. Барлық тапсырма офлайн симуляциямен жұмыс істейді. Кеңестер жоқ, өту үшін ұпайдың кемінде 75%-ын жинау керек.

  • Функция мен кілт атауларын тапсырмада берілгендей жазыңыз.
  • Алдымен шағын мысалмен print арқылы тексеріп, сосын «Тексеру» батырмасын басыңыз.
  • Есіңізде болсын: сүзгіден кейін қайта қалыпқа келтіру, retry тек уақытша қатеге, модельдің шығысына сенбей тексеру.
